# Contributing to LangGoap

Hi there! Thank you for even being interested in contributing to LangGoap.

LangGoap is an open-source Goal-Oriented Action Planning framework built
on top of the LangChain/LangGraph ecosystem. It is maintained by
[Integrallis](https://integrallis.com). We follow the same general
contribution style as the upstream LangChain projects so that moving
between repositories feels familiar.

## Pull request requirements

> **All external pull requests must link to an issue or discussion where
> a solution has been approved by a maintainer. PRs without prior
> approval will be closed.**

All pull requests should demonstrate meaningful effort and contextual
understanding. If the effort required to create a pull request is less
than the effort required for a maintainer to review it, that
contribution should not be submitted. Low-effort, drive-by
contributions — regardless of how they are produced — often miss the
mark on contextual relevance, accuracy, and quality, and are the
open-source equivalent of a denial-of-service attack on our review time.

The following requirements must be met for all external pull requests:

- The pull request must link to an issue or discussion where a solution
  has been approved by a maintainer.
- The pull request must fill in the repository's pull request template.
- The pull request must pass `make check` locally and in CI.

Maintainers reserve the right to close PRs without comment if these
requirements are not met. We will close pull requests and issues that
appear to be low-effort spam.

## Language policy

**All contributions must be in English.** This includes commit
messages, PR titles, PR descriptions, issue bodies, comments,
docstrings, identifiers, and user-facing strings.

## Development setup

LangGoap uses [`uv`](https://docs.astral.sh/uv/) for dependency
management and virtual environments.

```bash
git clone https://github.com/integrallis/langgoap.git
cd langgoap
uv sync --extra optimization
```

The `optimization` extra installs Google OR-Tools, which the CSP
integration tests rely on. Every CI job pins the same extra, so a
fresh clone that omits it will see CSP tests fail locally even when
`main` is green.

## Running the suite

```bash
make format       # isort + black
make lint         # format + mypy
make test         # fast default (skips api-marked live-LLM tests)
make test-all     # everything, including live-LLM tests (needs keys)
make check        # lint + test
```

Live-LLM tests look for `OPENAI_API_KEY` and `ANTHROPIC_API_KEY` in a
local `.env` file at the repo root. They self-skip when keys are
missing, so `make test` is safe to run without credentials.

## Test-first, integration tests before notebooks

Per the project policy, every new feature lands in this order:

1. Write an **integration test** that exercises the complete
   interaction (TestContainers for any external infrastructure).
2. See the test fail.
3. Implement the feature until the test passes.
4. **Then** create or update a notebook that demonstrates the same
   interaction as runnable documentation.

Notebook output must reflect real behaviour — mocks, skipped cells,
and trivially-passing tests are not acceptable. Each featured
notebook in `examples/tutorials/` maps 1:1 to an integration test
under `tests/integration/`.

## Commit and PR title conventions

LangGoap uses [conventional commits](https://www.conventionalcommits.org/).
PR titles should follow the format:

```
TYPE(SCOPE): DESCRIPTION
```

Examples:

- `fix(planner): resolve A* tie-breaking regression`
- `feat(csp): add multi-plan optimization via CP-SAT`
- `test(interpreter): cover the Anthropic structured-output path`

Accepted types:

- `feat` — new functionality
- `fix` — bug fixes
- `refactor` — behaviour-preserving changes
- `test` — test-only changes
- `docs` — documentation-only changes
- `perf` — performance improvements
- `chore` — tooling changes with no user impact
- `ci` — CI/CD pipeline changes

Accepted scopes (use the one that best fits; omit for cross-cutting
changes):

- `planner` — A* planner and search
- `csp` — CSP optimizer and CP-SAT integration
- `graph` — state, nodes, builder
- `interpreter` — natural-language goal interpreter
- `tracing` — tracing and history
- `viz` — plan visualization
- `prebuilt` — `create_goap_agent`, `goapify_tool`, subgraph helper
- `examples` — notebooks and tutorial code
- `docs` — documentation
- `ci` — workflows and release tooling

Commit messages should describe **what the code does and why**, not
the development process play-by-play. Reference relevant literature
or reference implementations when it clarifies the decision. Do
**not** include AI attribution (`Co-Authored-By: Claude`,
"generated by", etc.) in commit messages or PR descriptions.

## Dependencies and the lockfile

Do not update `uv.lock` or add dependencies to `pyproject.toml` (even
optional ones) unless you have explicit permission from a maintainer
as part of an approved issue or discussion. Dependency changes ripple
through every downstream consumer and are evaluated carefully.
